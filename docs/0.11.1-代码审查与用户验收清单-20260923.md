# 风吟 0.11.1：代码审查与用户验收清单

审查日期：2026-09-23。范围：9 月 21—23 日的 0.10.0、0.11.0、0.11.1 变更，以及此次重构必须保住的既有功能。本轮仅审查，不修改产品代码。

## 一、结论和边界

**不能认定 0.11.1 已完整落实全部要求，也不能认定它已达到稳定低延迟的发布标准。** 不是所有功能都只有界面：真实音源压力探测、内置音色 DSP、独立混响、共享输出、伴奏混音、MIDI 时间戳队列均已有实现；但存在以下确定的逻辑缺陷、部分实现和验证缺口。

- 本地审查提交：`614c8d1`，版本号 0.11.1；前序 `bd5a1ac` 为 0.11.0。
- 已发布 Windows 构建：[35815325867](https://github.com/JiaoRich/fengyin/actions/runs/35815325867)，本次查询状态 success，构建提交 `d527c641311b13e66082b2a487e0810a6a4b7df9`。此前通过 API 上传，远端提交号与本地不同。
- 本次重新运行 `python3 -m unittest discover -s tests -p 'test_*.py'`：46 项通过。
- 未在本轮运行 Windows、真实电吹管、SWAM 或空音；没有测得你电脑的端到端延迟，也未对安装包做逐字节源码一致性验证。不能将静态审查等同实机通过。
- 原 `low-latency-0.11.1-plan.md` 全部打勾的结论过于乐观，尤其“演奏中不重启”“测试覆盖充分”等，应以本报告的保留意见为准。

状态含义：**接通**＝存在完整方向上的事件/后端处理，不代表实机合格；**部分**＝实现范围不足；**缺陷**＝从代码可确认有违预期；**待测**＝真实设备/音源才能判定；**延期**＝用户主动推迟，不算遗漏。

## 二、应先修复的发现

### F01 高优先级：正在吹奏也会被当成空闲

`native/Source/MainComponent.cpp:992` 使用 `snapshot.breath < 4`。同文件 837 行将气息按 0～1 处理，MIDI 服务也输出该范围。因此有气息时这个条件仍成立。

后果：满足设备变更/需优化条件时，持续吹奏可能触发重启、静音探测。不是每次演奏必然触发，但安全保护失效。加载音源/方案的 1520、1602、2025 行也直接开始优化；手动优化 412 行没有完整的伴奏/吹奏互斥流程。智能音效开关 402 行另有直接调用设备优化的旁路。

验收：持续吹奏、播放视频、录音、切换方案分别覆盖；除用户明确确认外，不应被后台优化静音、重启或中断。优化开始后，也要阻止冲突操作或安全取消。

### F02 高优先级：旧版本升级可能跳过新版真实优化

`AudioDeviceService.cpp` 启动配置先保存 `audioSetupRevision` 为新版本（约 210 行）；`needsAutomaticLatencyTuning()` 420 行再依赖同一个版本字段和已测试设备名判断。旧版本留下的相同 `automaticLatencyTunedDevice` 不一定被作废。

后果：同一设备从旧版升级，可能直接被认定无需新测试。“新安装正常”不能覆盖“旧设置升级”场景。

验收：保留 0.11.0 的设置覆盖安装，首次加载音源必须执行新版必要验证；后续才可复用有效结果。

### F03 高优先级：优化结束不一定代表找到了稳定、实际应用成功的配置

`AudioDeviceService.cpp:559` 起：应用最佳候选的返回值被忽略；所有候选不稳定时仍可保存 tuned 标记。候选主要为当前设备最小值至 256，并未全面搜索其他共享驱动。`applyLatencyCandidate` 主要检查 ready，没有严格对照最终周期与要求一致。

验收：应用失败应恢复有效配置且不显示成功；无稳定方案应明确提示，不能记为“已验证”；从普通共享模式点击智能优化也应有机会切到支持的低延迟共享模式。

### F04 高优先级：压力测试与进度显示没有达到承诺范围

`PluginHostEngine.cpp:49` 探测真实插件，但只用音符 67、CC2/CC11；没有验证插件是否真的产生信号，也没有自动构造视频解码及伴奏负载。空音实际气息路径还包含 CC1，探测路径并不等价。

`prototype/app.js:1187` 的进度为每 1.5 秒推进固定阶段，包含“比较驱动”“模拟伴奏”等文案，而候选实际只比较当前类型/设备的缓冲区。它不是实际检测完成百分比。未知/不支持的 xrun 计数被按零处理，不能视为无掉帧证明。

验收：进度来自真实阶段；未加载采样、静音插件、空音、播放伴奏的资源压力均不可假通过；不能只凭 3.5 秒短测承诺长期稳定。

### F05 高优先级：并未完成全链路实时安全验证

`PluginHostEngine.cpp:109` 仍调用 JUCE AudioProcessorPlayer。所用 JUCE 9.0.2 回调内存在 player 锁、processor callback 锁，MidiMessageCollector 内也有锁。因此不能宣称音频路径已经完全无锁。保留框架锁不等于必然爆音，但需要证明不会竞争阻塞。

新增 SPSC 队列要求单生产者；`MidiInputService.cpp:281` 移调逻辑会从控制线程发送 noteOff，而 MIDI 回调也写队列；未看到统一保证单生产者的措施，存在并发风险。collector 预留 64 KB 不等于下游所有 MIDI 缓冲都已预分配，8192 槽队列也未配套最坏负载容量证明。技巧值仍由 `MainComponent.cpp:1031` 的界面定时器刷新，UI 卡顿可能影响技巧响应。

验收：并发 MIDI＋移调、密集 CC、开插件窗口、拖动 UI、录音开始/停止须有压力测试、丢事件计数和回调耗时证据；不应只检查源码出现了 ringbuffer。

### F06 高优先级：新增队列测试在 Release 下可能空跑

`tests/test_realtime_midi_queue.cpp` 将 push/pop 及所有验证放在标准 `assert` 中。Windows 构建脚本使用 Release，CMake 未为此测试解除 NDEBUG；断言及其中的调用在这种构建下会被移除。

46 项 Python 检查大量为源码字符串/结构断言，本次全部通过仍没拦住 F01。应补充真正的行为、升级迁移、失败恢复与实时压力测试；不能用“10 个 CTest 通过”证明所有功能有效。

### F07 明确不一致：弯音不是原值直通

`MidiInputService.cpp:575` 仍乘 `pitchSensitivity`（设置范围 0.25～2），然后夹到 -1～1；`PluginHostEngine.cpp:444` 再量化回 MIDI。旧设置仍可能改变弯音，端点也并非逐值一致。

验收：相同弯音输入在其他宿主与风吟、相同 SWAM 范围下结果一致；旧灵敏度不得悄悄缩放。目标是透传弯音消息，不是从 MIDI 推测管子的半音范围。

### F08 明确不一致：专业设置参数标签与实际算法，以及保存回读

前端有 `Low Shelf EQ`，但 `MainComponent.cpp:1765` 的 bass 实际参与 warmth 与 saturation，并非独立可配置低架 EQ；DSP 是简化音色处理，没有独立低架频率/增益参数。不能把这个标签当成已完成专业 EQ。

同文件 1147～1148 行将 bass 与 warmth 都回读为 warmth。写入时 warmth = 0.82×warmth + 0.18×bass，且 saturation 又受 bass 改变。因此不同的两个输入无法原样回读；打开后即使不想改变音色，再次保存也可能改变 saturation。编辑既有方案沿用 ID 的逻辑已在，但参数往返不完整。

验收：设置不同 bass/warmth，保存、重启、编辑应保持各项原值；直接“保存修改”不应使声音变化。专业名称必须对应真实参数。

### F09 部分：空音不能称为全系列已验证完整支持

已实现品牌识别、27 项别名目录、引擎程序选择、CC1/CC11 气息、插件状态保存；但乐器列表来自当前已加载空音实例的 program 名称匹配（`MainComponent.cpp:1236`）。它不是全磁盘采样库枚举；不向宿主暴露程序的库、别名未匹配库或需手动加载采样的库无法据此自动完善列表。切回 SWAM 后还需检查空音列表是否退回引擎卡片。

技巧主要依赖插件参数发现，不能保证所有空音 keyswitch/特殊控制都已覆盖。需要按用户实际安装的空音版本和库逐个验证，不应将 27 项目录等同 27 个已测试乐器。

### F10 部分：耳机跟随、伴奏原声和延迟显示有边界

- 系统输出变化主要每约 2 秒检查，且伴奏/录音时延后；不是插入耳机立即保证切换。Windows 必须实际改变默认输出才能触发该机制。
- 伴奏已在乐器 EQ/压缩/混响之后混入，取消了持续总线压缩，这是实质实现。但 `MasterOutputService.cpp:165` 对总和超过 1 的采样仍做安全衰减；两路太响时依然可能失真。不能保证任意音量相加后伴奏完全不变。
- 延迟显示是设备缓冲/报告延迟加插件报告值的估算，不是 MIDI 到耳机的实测；声音设置与顶部使用的估算项还不完全相同。
- `sharedMixRate()` 返回当前设备采样率，不能单凭此函数证明直接查询且锁定了 Windows 混音格式。应验证 44.1/48 kHz 系统设置与实际打开格式。
- xrun、插件延迟、MIDI 丢失计数已有后端字段，但前端未完整展示，也没有完整的一键诊断记录链路。

## 五、你这次安装，先测试这八件事即可

1. 覆盖安装后截图声音设置：驱动、设备、采样率、缓冲。记录电脑型号、耳机是有线还是蓝牙。
2. 加载常用音源，等优化结束，先不放视频连续吹两分钟：起音跟不跟手、有无断音。反馈 UI 延迟但不要把它当实测值。
3. 同一段加视频伴奏吹五分钟，比较是否明显变差；先降低两路音量，避免过载掩盖问题。
4. 风吟吹奏同时放浏览器声音，确认共享；再检查插耳机两路声音是否一起切换。
5. 硬件技巧学习一次；气息吼音分别三个灵敏度，检查强吹触发/换音误触。
6. 自定义方案把低频/温暖度设不同值，保存后重新编辑，对照数字；不要覆盖重要原方案，建“验收测试”副本。
7. 拖混响最小/最大、切三风格，确认听得到变化；自定义加载后显示你的命名。
8. 录十秒伴奏＋吹奏并回放；退出重开确认音色、授权和声音设置正常。

反馈模板：`编号｜通过/异常｜发生前做了什么｜驱动/缓冲｜截图或短视频`。先测日常正常路径；并发重配/极限队列/失败注入等应由开发方测试，不能把排查成本转给你。
