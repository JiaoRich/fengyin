# 空音切换后无声：证据与定向修复

## 确认的宿主错误

0.16.8 的 RecordingAudioProcessorPlayer::addResetMessages 在每次性能复位时发送
CC11=0、CC2=0、CC1=0。PluginHostEngine::breathChanged 在空音模式下只发送 CC1。
因此 CC11 清零后不会随吹奏恢复。该复位同时用于加载、MIDI切换及优化探测结束。
创建时用户在原厂界面选择奏法发生于初始复位之后；重载方案则先恢复乐器，再复位。
这解释了为什么同一组保存数据在两条路径下可能表现不同。

本机已有的官方 QinEngineV3 3.17.2 arm64 可执行文件（仅静态检查，未安装）证据：
- processBlock 中 0x7de64 判断 MIDI CC，0x7de90 判断控制器 11；
  0x7dea4 将值存入乐器运行时字段 0x178，并更新声部的表情值。
- 0x7dfb4 单独判断 CC1，进入另一条控制路径。
- 渲染路径 0x7f9e4 读取 0x178，后续用于音量计算。

这支持“CC1 与 CC11 不是可互换的一条控制”的判断。
该二进制不是用户 Windows 3.11，不能替代用户版本的实际音频测试。

## 成熟宿主对照

JUCE 9.0.2 AudioPluginHost 的 PluginGraph.cpp createNodeFromXml 保存/恢复完整
插件状态和总线布局；没有在恢复后强行将 CC11 设为0的步骤。
Steinberg 的 VST3 Persistence 文档要求同时处理组件和控制器状态，框架承担该工作：
https://steinbergmedia.github.io/vst3_dev_portal/pages/FAQ/Persistence.html

本轮不更改 KAM、不拼装新的插件状态、不模拟原厂奏法切换、不重写气息曲线。

## 改动

- 空音复位：停止旧音符、CC11恢复127、气息CC1归零、弯音回中。
- SWAM保留原复位语义，避免扩展改动影响已正常工作的音源。
- 在播放器接入新插件之前设置复位策略，覆盖 SWAM/空音交替切换。
- 抽取实际使用的复位函数，测试100轮交替切换、持续吹奏以及停止音符的顺序。

CC11=127是释放独立表情衰减，不会把用户效果链或主音量设成最大。

## 验收边界

- 自动测试证明实际复位函数不会将空音留在 CC11=0；不是空音音频实测。
- 本机编译只能证明macOS目标可构建，不能证明Windows空音3.11发声。
- Windows需验证：二胡、笛子创建后发声；切SWAM再切回发声；空音之间切换发声；
  退出重开后发声；不打开原厂界面即可发声；优化结束、MIDI重连后仍发声。
- 在上述实测前，只能称为“修复已证实的宿主MIDI错误”，不称“空音兼容性100%通过”。

## Windows首次构建失败后的授权修复

构建36318355199的主程序编译成功，13项测试中的旧授权兼容性断言失败，
因此没有进入安装包生成阶段；performance_reset_controllers测试通过。
诊断包SHA256为f40e43000bfdb6864dee40f3b38a7f1fda2611777d91b62a85976b675970caaa。

检查发现RSA校验把整数转成十六进制字符串，与固定64位SHA256文本直接比较。
整数会丢弃前导0，导致部分合法签名被拒绝，且具体是否遇到取决于机器码和授权编号。
新增固定测试用例在未修复代码上复现失败（摘要028159406a5f53b6b94ad160179150d1d6c490cd49f66e5d7b5678fa74cd8e00）。
修复为整数值比较，不变更密钥、签名格式、设备绑定规则，不跳过授权测试。
Windows首次失败日志未输出实际摘要，最终仍以重新运行Windows测试结果为准。
